# econ

## When to use

- Prices, probabilities, currencies, Sources, Sinks, or conversions change for a game pack.
- `EconConfig.luau` looks stale, or balance needs a simulation before shipping.

## Steps

### API 1 source and simulation (supersedes collect-only steps below)

econ.yml.genre_contract contains api=1, order, configs, optional recipe. Each
package validates its concrete schema. `forge codegen <slug>` writes GenreConfig
for this format; no marker retains legacy EconConfig. Invalid/future markers fail.
New-pack econ.yml is hand-owned; plan-pack econ.yml is generated from package
generator defaults and generation inputs. Only collect uses the legacy template
plan block/tuner; do not assume every generator records generatedBy.

`econ sim` for API 1 runs trusted package drivers through the real Executor/adapter
with injected seed/clock. Metrics are balances/sources/sinks/accepted/rejected
actions; zero accepted actions fail. Collect egg targets are not universal.
Singles use their package driver. A selected recipe uses its owner's declared
recipe driver once on a fresh full-pack executor, producing one coupled row.
Check compares GenreConfig for API 1 sources and EconConfig for legacy sources;
both use the same generation function as codegen. Actual simulation and generated
runtime execution remain separate evidence.

garden-defense-v1 has exactly one Coins wallet owner: grow-harvest. Survival uses
grow's walletPort and must have startingBalance zero. Only grow's save slice
contains balance; composed survival contains upgradeLevel. Crop sale funds
defense, wave reward credits the same wallet once. To prove farming is necessary,
the recipe's generation normalizer sets both standalone starting balances to zero.
Its coupled driver exercises the farm/sale/upgrade/wave chain. One version-1 envelope persists
player inventory/rewards/upgrades; server waves/matches/votes remain ephemeral.
No rewards in replayable persistence callbacks; legacy collect saves do not migrate
implicitly. Generic starters have empty monetization, not fabricated grant handlers.

### Legacy collect workflow

1. Change the pack's economy **source**, not its generated output. Which file that is
   depends on how the pack was made:
   - A pack scaffolded with `forge new` has a hand-authored `games/<slug>/econ.yml`.
     Edit that file — it is the pack's source of truth (currencies, Source, Sink,
     conversions, prices, probabilities).
   - A pack generated by `forge plan` has a **generated** `econ.yml`: its first line
     reads `# GENERATED by forge plan from genres/<genre>/econ-template.yml. Do not
     edit.`, and `forge plan` treats that header as proof the pack is safe to
     regenerate and overwrite. Hand-editing it is silently discarded by the next
     `forge plan`. For those packs the real source is the genre's
     `genres/<genre>/econ-template.yml` `plan:` block plus the concept and seed
     passed to `forge plan` (the exact command is recorded in the pack's
     `game.yml` as `generatedBy`).
2. Regenerate the legacy collect code: `lune run cli/forge codegen <slug>`
   (writes `games/<slug>/src/shared/EconConfig.luau` with byte-stable, deterministic
   key order; default pack is `kaiju-egg-raiders`).
3. Run check for EconConfig or GenreConfig drift according to the source format.
4. For legacy collect, check balance with the agent-based multi-actor simulation:
   `lune run cli/forge econ sim --pack <slug>` — N bots per server model 1-3 play
   sessions per day (10-40 minutes each), income from the top `income.activeSlots`
   owned kaiju, buying the most expensive affordable egg, hatching from the egg pool
   by weight, and a siege every 10 minutes of play that steals up to 10% of a
   rival's free-produced Common value (Robux-sourced kaiju are never eligible). The
   report covers inflation, the first-pay friction point, and bottlenecks. It does
   NOT model trading or price discovery — do not look for trade-driven balance
   findings in its output.
5. After launch, compare the same-named Economy Events logs against the sim report.

## Rules

- Never hand-edit a generated file: EconConfig and GenreConfig are generated, and for a
  pack produced by `forge plan` so is `econ.yml` (see step 1 for where its real
  source lives).
- **Paid Robux items must be deterministic**: Robux sells only deterministic items, and
  random hatching runs only on free currency.
- Price or probability changes require a human-merged PR; agents propose, humans merge.
- Game packs never copy or modify core or genre code — new economy behavior is config
  options or hooks (genre `econ-template.yml` seeds new packs via `forge new`).
- No network calls in specs; no secrets in output.

## Verification

- Re-running `forge codegen` produces no diff (byte-stable output).
- `lune run cli/forge check` exits 0 with no `econ drift:` failure.
- `forge econ sim` report exists and its balance findings are reviewed before shipping.
