# Release authorization

Local quality approval, credentials, and human external-release authorization are separate requirements. A source archive, normal build, starter profile, successful offline plan, or HTTP request fixture does not approve a production release.

## Local authorization

Assessed production quality requires a real Git source checkout with a resolvable
`HEAD^{tree}` at the input root. `qualityreceipt` executes
`git -C <input.root> rev-parse HEAD^{tree}` and refuses a missing tree; an archive
manifest is not a substitute. Gitless source archives support the starter and
headless build/check workflow, not assessed production approval. Do not initialize
or fetch a synthetic repository in an extracted archive to manufacture approval.

UNIT quality fixtures load the unchanged receipt and caller modules with a narrow
process seam for that exact tree query. They exercise current validation and
stale/missing-tree refusal without depending on the outer checkout's history.
The seam is test-only and is never loaded by production commands. The historical
collect-raid comparison ships the original scaffold blob
`ae633cef5e1525da65d9202007b0f89e906b14b2` from commit
`66dd6e934e6d31252e19aa1a32fd944574c2281d`, pinned by SHA-256 in its spec;
archive checks still compare original and current generated bytes.

`deploy plan --env production --pack <slug>` and `deploy --env production --pack <slug>` require a declared release-candidate profile and current approved receipt before report writes, builds, or network requests. Legacy packs without `quality.yml` fail with `LEGACY_UNASSESSED`; normal `forge build` remains available without retrofitting those packs. Nondevelopment staging uses the same assessed release requirement.

`deploy plan --env staging --pack <slug> --development` is an explicit, named development exception. Its `STAGING_DEVELOPMENT` result never grants release approval. It cannot be used for production, a declared release-candidate, or a downgraded quality target. Duplicate deploy flags and unsupported target flags are refused.

The gate delegates to `qualityreceipt.check`, using receipt and attestation schema 2. That contract checks current source/config/assets/rubric/evidence/build digests and independently validates the runtime evidence before returning `APPROVED`. The receipt carries capture schema 2, `buildIdentity = {schemaVersion: 1, id, source, config, asset}`, and `inputs = {buildPath, evidenceDir, evidence}`. Runtime validation compares the current build identity with `<buildPath>.identity.json`, the artifact hash, and actual server/client session and actor evidence. Missing, malformed, inconclusive, mutated, or stale evidence is not a compatibility exemption. These are local hash attestations, not cryptographic signatures.

An assessed release publishes the exact existing approved artifact instead of rebuilding it during deploy. Rebuild with `forge build`, collect current evidence, and obtain a new receipt before attempting release of changed bytes. Development staging uses `buildtargets.runTarget` to produce an inspected place and identity sidecar. The final gate is checked again before upload, and the upload uses bytes held across that check; an artifact replacement during the check refuses publication.

## External authorization

An offline plan requires no API key and does not call Roblox APIs. Its machine-readable output records `externalReleaseAuthorized: false` and `apiVerified: false`, even when local quality is approved. Product and gamepass actions in the plan are proposals, not implemented API operations.

Live publishing additionally requires `ROBLOX_STAGING_API_KEY` or `ROBLOX_PRODUCTION_API_KEY` for the selected environment, with exact decimal `ROBLOX_<ENV>_UNIVERSE_ID` and `ROBLOX_<ENV>_PLACE_ID` bindings matching positive integer IDs in `deploy.yml`. There is no `ROBLOX_API_KEY` fallback. Equal loaded environment keys and overlapping configured targets are refused. Production also requires `FORGE_ALLOW_PRODUCTION=1`. This environment switch records operator intent; it does not prove a human-merged PR or grant permission to an agent. Repository policy still requires human-merged production approval and explicit external-release authorization. Never record credential values in evidence. Operational error codes, one-attempt publishing, and fail-closed transport support and unproved live-pilot limits are documented in [Operations](operations.md).
